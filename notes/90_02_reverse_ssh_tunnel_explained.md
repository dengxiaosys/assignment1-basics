# 反向 SSH 隧道原理：为什么 B 能通过 A 操作 C

## 0. 问题背景

当前网络拓扑：

```text
Mac A ──可访问──> Linux B（开发机）
Mac A ──可访问──> Linux C（GPU 机）
Linux B ──不可直接访问──> Linux C
Linux C ──不可直接访问──> Linux B
```

目标是在 B 上执行：

```bash
ssh cuda-via-a
```

并最终登录 C。这里的“直接操作”是**使用体验上的直接**：命令从 B 发出，但底层流量仍经过 A 中转。

---

## 1. 核心命令

在 A 上建立隧道：

```bash
ssh -N \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=15 \
  -o ServerAliveCountMax=3 \
  -R 127.0.0.1:2222:192.168.71.6:22 \
  online1
```

在 B 上连接：

```bash
ssh -p 2222 dengxiao@127.0.0.1
```

其中：

- `online1` 是 A 的 SSH config 中对 B 的别名；
- `192.168.71.6:22` 是 A 能访问的 C 的 SSH 地址；
- `127.0.0.1:2222` 是隧道在 B 上创建的监听地址。

---

## 2. `ssh -R` 的语法

反向端口转发的形式是：

```text
ssh -R [远端监听地址:]远端端口:目标主机:目标端口 SSH服务器
```

代入本例：

```text
-R 127.0.0.1:2222:192.168.71.6:22 online1
```

逐项解释：

| 部分 | 含义 |
|---|---|
| `online1` | A 主动连接的 SSH 服务器，即 B |
| `127.0.0.1:2222` | 在 SSH 服务器 B 上创建监听端口 |
| `192.168.71.6:22` | 收到连接后，由 SSH 客户端 A 去连接的目标，即 C |
| `-R` | 监听端口位于远端 B，因此叫 Remote Forward |
| `-N` | 不在 B 上执行 shell 命令，只建立转发 |

最容易混淆的是：**目标 `192.168.71.6:22` 由 A 连接，不是由 B 连接。**

这正是该方案能够绕过“B 无法访问 C”的原因。B 只需要访问自己的 loopback；真正访问 C 的动作由 A 完成。

### 2.1 执行后对 B（`online1`）产生了什么影响

是的，命令成功后已经改变了 B 的**当前运行状态**，但没有永久修改 B 的系统配置。

建立过程如下：

1. A 上的 SSH 客户端连接并认证到 B（`online1`）；
2. A 向 B 的 `sshd` 发送一条“remote TCP forwarding”请求；
3. B 的 `sshd` 在 B 上创建一个监听 socket：`127.0.0.1:2222`；
4. B 为这条 SSH 连接保留一个 sshd 会话、监听端口、文件描述符和少量内存；
5. 后续 B 上任何进程连接 `127.0.0.1:2222` 时，B 的 sshd 才把该连接交给 A；
6. A 收到请求后，再临时建立到 C 的 `192.168.71.6:22` 连接。

因此，外层隧道建立成功后可以立即在 B 上观察到：

```bash
ss -ltn '( sport = :2222 )'
```

预期包含：

```text
LISTEN ... 127.0.0.1:2222 ...
```

若有权限，也可以查看监听进程：

```bash
sudo lsof -nP -iTCP:2222 -sTCP:LISTEN
```

监听者通常表现为 B 上为该 SSH 会话服务的 `sshd` 进程，而不是 C 的 sshd。C 的 sshd 只会在 B 真正连接 2222 后收到由 A 发起的新连接。

命令对 B 的具体影响：

| 影响 | 是否发生 |
|---|---|
| B 的 `127.0.0.1:2222` 被占用并开始监听 | 是 |
| B 上多出一个存活的 SSH/sshd 会话 | 是 |
| B 的 SSH 登录日志可能记录本次连接和端口转发 | 是 |
| 修改 B 的 `/etc/ssh/sshd_config` | 否 |
| 修改 B 的路由表、DNS 或防火墙规则 | 否 |
| 在 B 安装软件或创建项目文件 | 否 |
| 立即在 A 与 C 之间建立业务连接 | 否；B 连接 2222 时才按需建立 |
| 向 B 局域网暴露 2222 | 否；它只绑定在 B 的 loopback |

这里的影响是**临时且有生命周期的**。A→B 的 SSH 连接一旦结束，B 的 sshd 会关闭监听 socket、释放 2222 端口和会话资源，不会留下需要手工清理的系统配置。

`-o ExitOnForwardFailure=yes` 很重要：若 B 禁止端口转发、2222 已被占用，或者监听创建失败，A 上的 SSH 命令会直接失败，而不是保留一条“看似在线但没有隧道”的连接。

## 3. 一次连接的数据路径

B 上执行：

```bash
ssh -p 2222 dengxiao@127.0.0.1
```

数据经历以下路径：

```text
┌───────────────────────────────────────────────────────────────┐
│ B                                                             │
│                                                               │
│ ssh 客户端                                                    │
│     │                                                         │
│     ▼                                                         │
│ 127.0.0.1:2222                                                │
│     │                                                         │
│     ▼                                                         │
│ B 上的 sshd（反向转发监听端）                                 │
└─────┬─────────────────────────────────────────────────────────┘
      │ 已建立的 A↔B SSH 加密连接
      ▼
┌───────────────────────────────────────────────────────────────┐
│ A                                                             │
│                                                               │
│ A 上的 ssh 客户端收到转发数据                                 │
│     │                                                         │
│     └──────── 新建 TCP 连接 ────────> 192.168.71.6:22         │
└───────────────────────────────────────────────┬───────────────┘
                                                ▼
                                      ┌───────────────────┐
                                      │ C 的 sshd         │
                                      │ 用户 dengxiao     │
                                      └───────────────────┘
```

从 B 的视角，它只连接了：

```text
127.0.0.1:2222
```

但这个端口并不是真正的 SSH 服务，而是 B 的 sshd 为 A 建立的**转发入口**。数据进入入口后，通过已有 A↔B SSH 连接到达 A，再由 A 发往 C。

---

## 4. 为什么叫“反向”隧道

建立 SSH 连接的方向是：

```text
A ──ssh──> B
```

但被创建的监听端口位于连接的**远端 B**：

```text
B:2222
```

端口流量再沿已有 SSH 连接“反向”回到客户端 A，因此称为反向端口转发。

三种常见 SSH 转发的区别：

| 方式 | 监听端口在哪 | 典型用途 |
|---|---|---|
| `-L` Local Forward | SSH 客户端一侧 | A 通过服务器访问服务器侧资源 |
| `-R` Remote Forward | SSH 服务器一侧 | 让服务器通过客户端访问客户端侧资源 |
| `-D` Dynamic Forward | SSH 客户端一侧 | 建立 SOCKS 代理 |

本例要求在 B 上出现一个可连接 C 的端口，而 A 是连接发起方，因此必须使用 `-R`。

---

## 5. 两层连接与两次认证

这个方案包含两层逻辑连接，不要把它们混为一次登录。

### 5.1 外层：A 登录 B

```bash
# 在 A 上
ssh ... online1
```

这一层负责：

- 建立 A↔B 加密通道；
- 在 B 上创建 `127.0.0.1:2222`；
- 使用的是 **A 登录 B** 的凭据。

### 5.2 内层：B 登录 C

```bash
# 在 B 上
ssh -p 2222 dengxiao@127.0.0.1
```

这一层最终连接的是 C 的 sshd，因此仍要完成 **用户 `dengxiao` 登录 C** 的认证。

反向隧道只提供网络通路，**不会自动授予 C 的登录权限**。可选认证方式：

1. 在 B 使用能够登录 C 的专用 SSH 私钥；
2. 在 A→B 会话中开启 `ForwardAgent yes`，让 B 临时使用 A 的 SSH agent；
3. 使用 C 允许的其它认证方式。

如果“端口可连接但认证失败”，说明隧道已经成功，问题只在第二层身份认证。

> `ForwardAgent` 只应对可信任的 B 开启。更严格的生产环境建议为 B→C 单独创建用途受限的密钥。

---

## 6. 为什么监听 `127.0.0.1`

命令明确写：

```text
-R 127.0.0.1:2222:...
```

这样 2222 只允许 B 本机访问：

```text
B 本机 -> 允许
其它机器 -> 无法连接
```

若监听 `0.0.0.0:2222`，可能把通往 C 的入口暴露给能访问 B 的其它机器，还通常要求 B 的 sshd 开启 `GatewayPorts`。本场景只有 B 自己需要使用隧道，因此 loopback 是更小、更安全的暴露面。

---

## 7. SSH 配置别名做了什么

在 B 的 `~/.ssh/config` 中：

```sshconfig
Host cuda-via-a
    HostName 127.0.0.1
    Port 2222
    User dengxiao
```

此后：

```bash
ssh cuda-via-a
```

只等价于：

```bash
ssh -p 2222 dengxiao@127.0.0.1
```

别名不创建隧道，也不改变网络拓扑；它只是保存连接参数。必须先由 A 建立 `-R` 隧道，别名才可用。

## 8. 如何判断故障发生在哪一层

### 8.1 B 上没有监听 2222

```bash
ss -ltn | grep 2222
```

没有输出，通常表示：

- A 上的隧道进程未启动或已退出；
- B 的 sshd 禁止端口转发；
- 2222 已被占用，而命令又没有成功建立监听。

在 A 上使用 `ExitOnForwardFailure=yes`，可以让端口创建失败时立即报错，而不是留下一个看似正常、实际不可用的 SSH 进程。

### 8.2 B 能连接 2222，但连接超时

```bash
ssh -vvv -p 2222 dengxiao@127.0.0.1
```

如果 TCP 已连通但随后超时，通常是 A 无法连接 `192.168.71.6:22`，应在 A 上验证：

```bash
ssh cuda
```

### 8.3 已看到 C 的 SSH banner，但认证失败

说明网络和隧道都正常，只需处理 B→C 的密钥、agent 或账号权限。

### 8.4 用一条远程命令做端到端验证

在 B 上：

```bash
ssh cuda-via-a 'hostname; nvidia-smi'
```

若输出 C 的主机名和 GPU 信息，B→A→C 的控制链路已经完整可用。

## 9. 隧道生命周期与保活

反向端口只存在于外层 A→B SSH 连接的生命周期内：

- A 休眠、断网或重启：隧道消失；
- A→B SSH 进程退出：隧道消失；
- C 上已经启动的训练进程：通常继续运行；
- B 想再次查看日志或执行命令：必须先恢复隧道。

测试阶段建议前台运行，方便看错误：

```bash
ssh -N -v \
  -o ExitOnForwardFailure=yes \
  -R 127.0.0.1:2222:192.168.71.6:22 \
  online1
```

稳定后再改成后台：

```bash
ssh -fN \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=15 \
  -o ServerAliveCountMax=3 \
  -R 127.0.0.1:2222:192.168.71.6:22 \
  online1
```

长期使用可安装 `autossh` 自动重连；Mac 还需防止系统休眠，例如用 `caffeinate` 包裹前台 SSH 进程。

### 9.1 如何主动撤销对 B 的临时影响

若隧道以前台方式运行，在 A 上按 `Ctrl-C` 即可。若使用 `-fN` 放到后台，先在 A 查找对应进程：

```bash
pgrep -af 'ssh.*127.0.0.1:2222:192.168.71.6:22.*online1'
```

确认 PID 后：

```bash
kill <PID>
```

随后在 B 验证监听已消失：

```bash
ss -ltn '( sport = :2222 )'
```

无输出就表示 B 上的临时监听已经释放。B 重启、B 的 sshd 重启或外层 SSH 会话异常断开，也会产生同样效果。

## 10. 与 C 挂载 B 代码的关系

“B 操作 C”和“C 实时读取 B 的代码”是**两个方向相反、互相独立**的通道：

```text
控制通道：B:2222 -> A -> C:22
文件通道：C:2223 -> A -> B:16101
```

- 控制通道让 B 执行 `ssh cuda-via-a 'command'`；
- 文件通道让 C 用 sshfs 挂载 B 的 `assignments/`；
- 两者同时存在，才得到完整体验：**B 改代码、B 发命令、C 读取最新代码并使用 GPU 执行**。

大数据、checkpoint 和 C 的 Python/CUDA 环境仍应放在 C 本地，不能通过 sshfs 读写。完整挂载步骤见 [跨机开发总指南](./90_01_cross_machine_dev_B_to_C_gpu_guide.md) §8。

---

## 11. 小结

1. `ssh -R` 在 SSH 服务器 B 上创建监听端口，目标连接由客户端 A 发起。
2. B 访问 `127.0.0.1:2222` 时，数据沿 B→A→C 转发，因此绕过 B 无法直连 C 的限制。
3. 外层 A→B 和内层 B→C 是两次独立认证；隧道只解决网络可达性。
4. 监听 `127.0.0.1` 可避免把入口暴露给其它机器。
5. A 的网络和 SSH 进程决定隧道生命周期；C 上已启动的训练不依赖控制会话持续在线。
6. 配合反方向的 sshfs 文件通道，可实现“B 开发和控制，C 执行 GPU 任务”。
